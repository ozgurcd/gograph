# Project: gograph

`gograph` is a local Go repository indexer for coding agents. CLI and the project MCP server share 64 repository query, analysis, and workflow capabilities; four additional session tools make 68 project endpoints. A separate workspace MCP server exposes status, query, path, and impact through the same native implementations as their CLI operations. CLI graph-backed commands read persisted `.gograph/graph.json`. Project MCP keeps source-analysis requests fresh in memory by default and can publish refreshed artifacts only when started with `--persist-refresh`.

## Positioning and onboarding

gograph is a local repository-analysis layer backed by persisted or in-memory graph state, not a replacement for every Go or search tool. Use `gopls` for live compiler-backed workspace diagnostics, navigation, implementations, and refactoring; use `rg` or other text search for literals, comments, generated/non-indexed files, and non-Go content. Use gograph for repository-level impact, reachability, application inventories, composed agent workflows, and policy gates. When graph precision is AST/fallback, results are ambiguous, or a known call is missing, cross-check with `gopls` or targeted source/text search and disclose the fallback.

The executable Go package is `github.com/ozgurcd/gograph/cmd/gograph`. First-run documentation must use repository-wide commands such as `stats`, `summary`, and `hotspot` before examples that require a project-specific symbol. Product claims must distinguish reproducible snapshot counts from inference and must not promise absolute accuracy, fixed token savings, or hallucination-rate improvements without published methodology and data.

CLI `explore` and MCP `gograph_explore` are one additive, bounded first-call capability over the shared `gograph.explore.v1` value. They rank deterministic lexical matches, disclose the selected symbol and whether it came from direct or ranked resolution, preserve ambiguity, and expose mutually exclusive compact, standard, and deep response modes. Compact defaults to five rows and retains discovery, selected node/role, complete totals, and explicit omissions without token-heavy evidence bodies. Standard preserves the original source, direct caller/callee/test, and exact identity-impact response with a default of ten rows. Deep defaults to 25 rows and adds bounded depth-3 exact identity callers/callees, selected package context, and an explanation. Explicit limits override the mode default and remain clamped to 1-100. Possible dispatch is excluded from bundled exact impact and deep traversal; synthetic forwarders are crossed transparently, and deep caller/callee rows retain stable identity, call-site provenance, and declaration location when indexed. Ambiguous selections omit deep expansion until an exact fully-qualified identity is supplied. Question-like input is tokenized lexically rather than interpreted by a model. Complete totals, truncation, and omission metadata direct callers to the existing focused commands when they need unbounded evidence or broader fallback traversal; those commands remain stable and authoritative.

## Published evidence and shareable entry points

gograph's current public proof package is source-controlled and reproducible. `benchmarks/testdata/refactor-shop` is a small reviewable Go fixture; `benchmarks/suite.json` declares its expected structural evidence and comparison workflows; and `scripts/benchmark.go` tests the fixture, requires a complete precise graph, repeats deterministic workflows, verifies every declared evidence string, and records exact commands, raw output, process calls, elapsed time, build health, revision/dirty state, and runner/suite/fixture SHA-256 digests. The checked-in v1.5.5 result is `benchmarks/results/gograph-v1.5.5.json`, and the no-install demo renders the identical JSON through `docs-site/content/demo.md` plus `docs-site/static/demo/`. Claims remain deliberately narrow: the suite does not establish fixed token savings, universal speed, hallucination rates, or end-to-end agent success.

The reusable 1280×640 social card is `docs-site/static/images/gograph-social-preview.png`. Hugo uses it as the site-wide Open Graph and Twitter image. The canonical deployable website inputs are under `docs-site/content/` and `docs-site/static/`; GitHub Actions rebuilds `docs-site/public/`, so generated output should not be treated as hand-maintained source.

Generated wiki package pages are cache output. After a successful `gograph wiki` run, obsolete generator-owned `packages/*.md` pages are pruned, while custom pages, `packages/README.md`, linked/special entries, and oversized unrecognized content are preserved.

## Analysis modes and health

Default builds produce an AST graph and tolerate partial parsing when at least one Go file succeeds. `BuildMetadata.Precision` records `ast`, `precise`, or `precise_fallback`; this is independent of complete/partial AST build health. Each successfully parsed source file stores a SHA-256 digest. A later build reparses every selected file in each changed package directory and reuses parser-owned records for unchanged packages; stats expose `reused_files` and `rebuilt_packages`. Precise builds reuse that AST base but still run repository-wide go/packages type loading plus CHA/SSA so cross-package method sets and dispatch remain correct. Missing indexed production files or type/load errors normally retain the AST graph and record a visible fallback instead of claiming precise success. A failed precise retry preserves an existing fresh successful precise artifact covering the same selected sources. `gograph build . --precise --strict` keeps that diagnostic artifact behavior but exits non-zero on fallback for CI and release gates. `gograph stats` and MCP stats expose precision, build health, and reuse counts. `gate` fails closed for stale source, but it does not currently reject a fresh graph whose build metadata is incomplete; CI workflows that require complete coverage must check build health explicitly.

Low-memory execution is an operational policy, not a weaker analysis mode. Repository builds, explicit workspace member refreshes, and project MCP startup/refresh accept `--memory-mode=low` with an optional `--max-memory` byte size. Low mode uses aggressive garbage collection, selective transactional precise-enrichment copies, and phase-boundary reclamation while preserving graph precision and failure atomicity. The configured value is a soft Go-runtime memory target, not an RSS or hard allocation cap; existing stricter runtime limits are preserved, and Gograph never silently omits precise facts to meet the target.

Test-call resolution is an independent capability bound to the exact graph artifact. AST graphs report `ast_heuristic` and retain selector-name attribution for compatibility. Precise builds run a separate non-fatal typed pass over compiling test packages: direct selectors, local method values, and single-assignment non-escaping interface locals whose concrete dynamic type is proven bind exact repository symbol IDs. Factory-returned, reassigned, escaping, and otherwise open interface values retain CHA/possible provenance. Broken or omitted test packages report `typed_partial` without downgrading otherwise successful production precision; a fully loaded typed test pass reports `typed_complete`. `untested` suppresses exact transitive paths, keeps possible descendants visible with an explicit count, and never treats an ambiguous parser-only short name as exact. Static attribution never proves runtime coverage.

Forward attribution is exposed by CLI `coverage` and MCP `gograph_coverage` through `gograph.coverage.v1`. Reverse attribution is opt-in through CLI `tests <symbol> --transitive` and matching typed `gograph_tests` parameters; both return the same native `gograph.tests.v1` report with every reaching test, representative stable-ID path, depth, and exact/possible propagation, while default direct `tests` behavior remains compatible. Ambiguous same-named tests or product symbols are never silently merged. CLI `identity` and MCP `gograph_identity` resolve canonical graph-v2 symbol IDs; the package qualifier handles in-package/external-test ID collisions without turning file or line into identity. `untested` reports canonical stable IDs in JSON/MCP and CLI `--wide`, and its repeatable CLI `--exclude` and MCP `exclude[]` use the same lexical repository-relative matching.

Scanner file selection and `go/packages` share one cmd/go-resolved build configuration: GOOS/GOARCH, cgo, compiler, user and GOFLAGS tags, tool tags, and release tags. First-class `--tags=<tag[,tag...]>` selects one validated context rather than unioning graphs; an explicit selection replaces only `GOFLAGS -tags`, while omission preserves inherited cmd/go behavior. The same explicit tags flow through repository AST/precise builds, typed test attribution, `stale`, project MCP startup/refresh and Git baselines, explicit workspace member refresh/validation, and workspace CLI/MCP queries. MCP capabilities report requested and effective tags. Active constrained tests remain indexed; inactive constraints, generated files, cmd/go wildcard-excluded directories, go.mod ignore paths, and Git-ignored paths do not enter any graph records. The persisted build-context fingerprint covers build and module-selection state; the selected inventory is compared separately. Together with per-file content digests, freshness checks detect tag/platform changes, module-boundary changes, active/inactive transitions, additions, deletions, and byte edits even when mtimes are preserved. Legacy graphs without digests keep an mtime fallback until rebuilt and are not eligible for parser-record reuse.

`gograph stale` is a tri-state freshness predicate in both text and JSON modes: exit `0` means current, `2` means stale, and `1` means an operational or JSON serialization error. Exit `2` is an expected freshness result and is recorded as successful session telemetry. Shell automation must distinguish `2` from `1`, especially under `set -e`, so genuine failures are not mistaken for rebuild requests.

## Precise call-graph representation

A dynamic interface invocation is devirtualized to one exact ordinary `CallEdge` only when SSA proves that its value contains one concrete dynamic receiver type; merely observing one repository implementation is never proof. Otherwise it is represented by one deterministic possible `CallEdge` per valid named in-repository CHA target. Parallel target edges retain the same source-expression provenance. User-facing caller/callee results deduplicate that expression, while depth traversal, impact, diagrams, reachability, orphan analysis, and test attribution follow every target and propagate uncertainty.

Promoted methods may appear in SSA as wrappers with no source declaration. Precise graphs retain the wrapper as the concrete interface target and add a `Synthetic: true` wrapper-to-declared-method forwarding edge. Synthetic edges have no source call site, remain hidden from presentation and source metrics, and consume no visible traversal depth.

Interface-qualified caller queries such as `OIDCStateRepository.Delete` resolve through precise `Implements` edges, including embedded interface method sets and promoted concrete methods. Bare names, concrete receiver dot notation, fully-qualified symbol IDs, and exact matching use the same resolver in CLI and MCP callers.

Repository `path`/`gograph_path` and workspace `workspace path`/`gograph_workspace_path` select one best relationship path through a shared deterministic ranking contract instead of accepting the first breadth-first route. Ranking is lexicographic: worst certainty (`exact`, then `ambiguous`, then `possible`), visible path length, production before tests, typed resolution before heuristics, and fewer cross-repository transitions; a canonical relationship/provenance key breaks complete ties. Repository calls without a resolved target identity are possible heuristic edges, while CHA targets remain possible but typed. Workspace exact-only traversal and explicit possible-edge opt-in remain unchanged. Synthetic forwarding is transparent to visible length. The established singular CLI/MCP response shapes remain compatible.

## MCP refresh policy

Source-analysis MCP tools check the effective selected-file inventory, build/module fingerprint, per-file content digests, source-policy version, and replacement of the persisted graph artifact. A persisted graph produced under a different effective `GOWORK` or build selection is stale: MCP must refresh it successfully or return the diagnostic, never silently serve mismatched facts. A later successfully decoded precise publication is adopted even when overlapping builds give it an earlier build-start `GeneratedAt`. A precise or precise-fallback session never adopts an AST-only downgrade. Source changes reparse changed package ASTs and reuse unchanged package records; precise mode still recomputes repository-wide CHA/SSA. Precise refresh failure is returned visibly while retaining fallback metadata for diagnosis and retry.

MCP refresh persistence is opt-in with `gograph mcp [path] --persist-refresh`; default and fixed plugin/MCPB launches remain in-memory-only. The option publishes the latest successful startup build or stale refresh to the fixed `.gograph` output bundle (graph plus nine reports), not a multi-branch or historical cache, and it does not edit `.gitignore`. Graph/report artifact publishers coordinate through the persistent operational file `.gograph/.artifacts.lock`, derive the new baseline from the immediately preceding persisted graph under that lock, stage and sync the complete bundle, then rename reports before `graph.json` as the commit marker. Same-directory replacements are atomic on Unix-like systems but are not guaranteed atomic by Go on non-Unix platforms; the ten-file bundle is not one atomic transaction, so a crash can leave reports ahead of the previous graph marker. Refresh publication rejects stale candidates and never replaces an equal or richer fresh graph with AST or precise-fallback output; manual builds remain authoritative except that a failed precise retry preserves an existing fresh precise artifact.

An initial MCP publication failure prevents server startup. A later refresh publication failure is returned by the triggering tool while the valid in-memory graph remains pending for a publication retry without a forced rebuild. Persistence-enabled tool annotations disclose filesystem mutation; tools that cannot refresh retain their original annotations.

Repository query, analysis, and workflow features have semantically equivalent CLI and project-MCP entry points; workspace status/query/path/impact have equivalent entry points on the separate workspace server. The normal mapping is `<command>` to `gograph_<command>`, with explicit alias, boundary-creation, and session mappings. The complete CLI-only boundary is build, validate, doctor, gate, snapshots, installation, project/workspace server startup, workspace build/member refresh, help, and version. `doctor` is a CLI-only host/artifact diagnostic rather than a repository query: it reports the running executable, PATH resolution, distinct installations, and safely comparable stable versions through `gograph.doctor.v1`, reading Go build metadata without executing alternate binaries. It also reports the current repository graph's availability, freshness, analysis mode, capabilities, artifact fingerprint, and bounded diagnostic. CLI presentation flags map to typed MCP parameters or structured content; callers, callees, impact, endpoint, dependents, deps, path, and coupling map CLI `--mermaid` to MCP `mermaid=true`. Output modes are command-validated and mutually exclusive. API/check baselines accept either a validated local Git ref or a saved graph path ending in `.json`. CLI audit sessions require `--intention` for analytical commands. MCP has no intention parameter; while a session is active it records observational command/duration/status telemetry without arguments or query results.

## Compatibility

The graph schema remains version 2. Precision, call-column, synthetic-forwarding, build-context fingerprint, source-digest, analysis-cache, parser/precise provenance, declared-interface-method, reuse-count, test-call-resolution, and typed test-target fields are additive JSON fields. Current readers normalize missing legacy precision to AST-only, missing test-call capability to `ast_heuristic`, and missing call metadata to ordinary line-only edges. Missing cache provenance disables reuse, and missing source digests use legacy mtime freshness until the next build. Older v2 binaries can decode new files, but may count or display synthetic forwarding records or typed test targets using older semantics; current binaries are required for the new traversal, presentation, test-attribution, grouped-route, and digest-freshness semantics.

## Static-analysis limits

Precise dispatch uses proof-backed SSA devirtualization where available and conservative CHA otherwise, so open calls can include named implementations that are not instantiated in one runtime configuration. Reflection, `unsafe`, plugins, unresolved function values, test-only packages, unnamed concrete types, module-external implementations, and incomplete package loading can still cause omissions. AST callback recovery filters known ordinary identifiers, but selector-valued arguments remain name-based and can create false call edges when a data field shares a name with a callable. Precise implementer edges use qualified IDs, while legacy ID-less graphs and the AST implementer fallback remain package-insensitive. Constant nested Gin/Echo/Fiber `Group` prefixes and Chi `Route` closure prefixes are composed; dynamically computed prefixes remain unresolved suffixes. Changed-route policy checks also normalize handler names and can conflate same-named handlers across packages or receiver types. Test attribution is static: possible interface targets do not satisfy exact coverage, partial typed loading preserves heuristic gaps, and neither exact nor possible edges prove execution. Treat zero-result and heuristic/fallback results as evidence to cross-check, not proof. Flow analysis remains path-insensitive with up to 16 call-site frames and query-time sanitizer policy; findings are review leads, not proof.

Non-goals include other languages, model APIs, SaaS, remote telemetry, source-mutating red-proof harnesses, and target binary/test execution. A red-proof workflow cannot honestly guarantee restoration across process crashes or concurrent editors and remains outside the structural-analysis trust boundary.
